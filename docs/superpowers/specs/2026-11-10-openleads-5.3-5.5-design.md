# OpenLeads 5.3 to 5.5: Simple, the model, the app

Date: 2026-11-10. Status: agreed in conversation with Samyar; this document is the
reference for planning. Items marked **(builder's call)** are left open on purpose.
Items marked **(Claude's call)** were decided by Claude and not explicitly by Samyar;
he can overrule them.

## 1. Intent

OpenLeads works, but it doesn't stick. Today it has seven front doors (40 CLI
commands, a chat REPL, a separate `assistant` command, 21 dashboard pages, 27 MCP tools,
a Python API, a JSON API) and three generations of automation running side by side
(v2 `campaign`; v4 recipes, watchers, drip, follow-up sequences and JSON templates;
v5 workspace sequences and templates plus 5.2 workflows). A new user can't tell
where to start, and a returning user has no reason to come back each day.

The goal of the next month is for OpenLeads to become **part of someone's daily
workflow instead of another open-source repo**: easy to start, it clicks the first
time, and it gets the basics right without fuss.

**Who it's for:** solo technical founders and the AI agents they work with (Claude
Code, Cursor, anything speaking MCP). Small sales teams and OSINT users still work
fine but are not who we design for.

**Why now:** the repo has 65 stars growing ~1.5/day from ~540 unique visitors per
two weeks (about a 3% visit-to-star rate). Samyar wants 1,000 stars, then to
monetize. More features won't do that; a product people use daily and a launch
moment that lands will.

## 2. Goals, non-goals, anti-goals

**Goals**
- One obvious way in: type what you want, see the plan, run it.
- A daily reason to return: the **Today** briefing.
- A tiny local model that understands requests and gets them right, invisible to run.
- A web app that looks and feels like T3 Code, in OpenLeads colors.
- Ship something to `main` every day; a release roughly weekly.

**Non-goals (this month)**
- Desktop app (dropped: no Apple Developer account, and the web app is enough).
- New lead sources or new CRM features.
- Removing old commands or breaking existing users' recipes, scripts or databases.
- Changing the license.

**Anti-goals (failure even if it technically works)**
- Fewer pages that hide the same complexity one click deeper.
- A model that is impressive in demos but wrong on ordinary requests, or that users
  notice (slow, heavy, a setup step).
- Emails that read like AI: em dashes, generic flattery, vague personalization,
  newsletter styling.
- Growth tactics that get Samyar's accounts banned or read as spam (mass issues or
  PRs on other repos, automated posting where a site forbids it).
- Breaking the "core installs with zero dependencies" promise.

## 3. Constraints

- **Python core stays stdlib-only.** New dependencies only behind extras (`[ai]`).
- **Local-first.** Nothing leaves the machine unless the user turns it on.
- **Users never need Node.** The 5.5 app is built in CI and shipped as static files
  inside the wheel. Contributors to the app need Node/pnpm.
- **Training happens on Samyar's MacBook M2 with 8GB RAM.** This bounds model size
  (about 0.5B parameters) and training method (LoRA with MLX).
- **The model is a public download, so it contains no real person's data.** Training
  data is synthetic plus Samyar's written copy rules. Nothing from the
  `~/Desktop/email people` folder's contact lists, send logs or replies.
- **License:** AGPL-3.0 with a commercial option (unchanged). T3 Code is MIT; keep
  its copyright notice with the forked code.
- **Samyar's time for growth: 15 to 20 minutes a day.**
- Existing tests (1,122, ~30s) keep passing; the nightly live benchmark keeps running.

## 6. 5.3: Simple

### 6.1 One way in: `openleads "..."`

Typing a request runs **say it, see the plan, run it**:

```
$ openleads "find 30 rust devs in Berlin and email them about our hiring tool"
Plan
  1. Find      30 rust developers in Berlin (github)
  2. Verify    keep safe emails only
  3. Write     email, angle: mutual signal, from your pitch
  4. Send      dry run (add --live to send)
Run it? [Y/n]
```

- Plain finds ("dentists in Austin") skip the confirmation and just run, as today.
- Anything that sends, schedules or changes the workspace shows the plan first.
- **A plan is a workflow graph** (the 5.2 format), so it runs on the existing executor,
  can be saved with one keypress ("save as workflow"), and opens in the editor. This
  replaces `assistant` as a separate concept; `openleads assistant` keeps working.
- In 5.3 the plan comes from the existing rule parser (`intent.py`, `assistant.py`),
  extended to emit graphs. In 5.4 the model takes over, with the rule parser as fallback.
- **5.3 parser scope (Claude's call):** the three intents `assistant.rule_interpret`
  already knows (search, campaign: find then write then send, and schedule), emitted as
  graphs, plus sequence enrollment ("add them to my 5-step sequence"). Other workspace
  actions (tag, move deal, create task) stay as commands and MCP tools in 5.3. The 5.4
  model covers them, and anything the rule parser can't plan says so and suggests the
  command.
- After running, OpenLeads answers in one or two plain sentences ("Found 28, 19
  verified. 19 drafts ready; run `openleads today` to review.").
- Bare `openleads` with no arguments still opens chat mode, which uses the same
  plan-then-run flow.

### 6.3 Today

One briefing that answers "what should I do now?", in priority order:

1. **Replies waiting on you**, positive ones first, oldest first. (From Samyar's own
   measured rule: answer a yes within a business day.)
2. **Emails ready to approve**: drafts from sequences and workflows waiting for a yes.
3. **Tasks due or overdue** (calls, LinkedIn, manual emails).
4. **New leads** from workflows and watchers since you last looked.
5. **Heads-ups**: bounce spikes, warmup cap reached, a source down, mailbox not connected.

Surfaces **(Claude's call, since Samyar left it to me)**:
- **Terminal:** `openleads today`, with one-key actions (approve, skip, open, snooze).
  Also shown when chat mode starts.
- **MCP:** a `today` tool returning the same data, plus `approve_draft` and
  `snooze`, so an agent can run the morning for you.
- **Web:** the home screen of the 5.5 app. In 5.3 the current dashboard's Home shows it.
- A morning email digest is out of scope this month.

Most data already exists: `workspace/stats.home` and `recommended`,
`workspace/tasks.counts`, `workspace/sequences.due_enrollments`,
`automate/workflow/store.due_waits`, `automate/watch.tick`, `outreach/inbox.scan`.
Today composes them. It adds only what the two points below need: a drafts queue and
stored reply text.

**Approve before send (Claude's call):** new workspaces default to approve-before-send
for first emails from sequences and workflows, so Today's approve queue is real.
Existing workspaces keep their current behavior. Follow-ups in an approved thread
send on their own.
- Waiting drafts live in a new `drafts` table (rendered subject and body, lead, the
  sequence enrollment or workflow run it came from, status). The enrollment or
  workflow wait it came from stays held until the draft is approved, edited and
  approved, or skipped. Workflow `send` nodes queue a draft instead of sending when
  approval is on.
- **Interactive runs send when you say so.** A one-shot `openleads "..." --live` that
  you confirmed at "Run it?" sends immediately; that confirmation is the approval.
  The queue is for unattended sends (sequences, scheduled workflows). Without
  `--live`, the one-shot run writes drafts into the queue, which is what the 5.3 example
  output's "19 drafts ready" means.
- `approve_draft` (MCP), approve in `openleads today` and approve in the app all send
  the draft through the normal sender, with its suppression, warmup and pre-send hook
  checks.

**Replies in 5.3 (Claude's call):**
- `inbox.scan` keeps the reply text locally (in the activity timeline for the contact),
  since Today needs a snippet and 5.4's reply sorting needs the text.
- 5.3 sorts replies with simple rules (out of office, unsubscribe, bounce,
  not interested, everything else "needs you"), ordered oldest first. 5.4's model
  replaces the rules.
- A reply counts as answered when a later message from you appears in the same
  thread, checked against the Sent folder when IMAP allows it, otherwise against
  what OpenLeads sent. If neither is available, it stays listed until you mark it done.

### 6.4 Copy rules everywhere OpenLeads writes

Apply Samyar's measured rules to the built-in writer, the quality gate and later the
model (section 7.4). In 5.3 the quality score gains checks for em/en dashes,
length over ~125 words, and vacuous personalization, and the writer stops producing
them.

### 6.5 Pre-send hook (from PR #31)

A generic, off-by-default check before any live send:
- Setting `presend_hook`: a shell command or an `https://` URL. It receives the email as
  JSON (to, from, subject, body, lead fields, whether it's a first email) and answers
  `{"action": "send" | "hold", "reason": "..."}`.
- A held email shows its reason everywhere a send result shows today and appears in
  Today under heads-ups.
- `presend_hook_on_error`: `hold` (default) or `send`, for timeouts and bad answers.
- Docs show Precleared as one example hook. Credit the PR #31 contributor.
- Whether the contributor or we build it is **(builder's call)**, depending on their reply.

## 7. 5.4: The OpenLeads model

### 7.1 What it does

One small model, four jobs, in order of importance:
1. **Request to plan:** text in, a valid plan out (a `Query` for finds, a workflow graph
   for anything else).
2. **Plain-text answer:** one or two sentences about what happened, from the real result.
3. **Reply sorting:** interested, not now, not interested, unsubscribe, out of office,
   bounce, wrong person (with the named person if given).
4. **Email writing:** first emails and follow-ups from the research brief.

Samyar's bar: "just do the basics right, no AI em dashes, human stuff". The model
should be so efficient and accurate that users can't feel it running.

### 7.2 Size, training, runtime

- **Base model:** an Apache-2.0 or MIT licensed instruct model around 0.5B parameters
  (Qwen-class). Pick by eval results **(builder's call)**.
- **Training:** LoRA fine-tune with MLX on the M2/8GB. Must fit in memory; batch size
  and sequence length are tuned to that. Training code and data generator live in the
  repo under `model/`, are not shipped in the wheel, and are reproducible from one
  command.
- **Shipping:** quantized (about 4-bit, target ~300MB), hosted on Hugging Face with a
  checksum, downloaded on first plain-English request to `~/.openleads/models/`.
- **Install:** `pip install openleads[ai]`. The runtime must install from prebuilt
  wheels (no compiler) on macOS arm64, Linux x86_64 and Windows; which runtime is
  **(builder's call)**.
- **Speed target:** a plan in under 1 second on an M-series Mac and under 3 seconds on a
  typical laptop CPU; email drafts in a few seconds.
- **Output:** each job answers in a fixed JSON shape; outputs are validated (and
  constrained during decoding if the runtime supports it). An invalid answer never
  reaches the user; it falls back.
- **Fallbacks, in order:** a configured OpenAI-compatible endpoint (existing setting)
  if the user set one; the OpenLeads model if `[ai]` is installed; the rule parser and
  built-in writer otherwise. No `[ai]` means OpenLeads behaves exactly as in 5.3.

### 7.3 Training data

Generated, never real:
- **Plans:** templates and paraphrases over every command, source, filter and workflow
  node, including typos, short forms and mixed requests. Labels come from the rule
  parser where it's right and from hand-checked rules where it isn't.
- **Answers:** synthetic run results paired with correct one-to-two-sentence summaries.
  Numbers in the answer are taken from the result, never generated.
- **Replies:** synthetic replies for each category, in many tones and lengths, including
  auto-replies and bounces.
- **Emails:** synthetic leads and briefs, with emails that follow the copy rules below
  and pass the existing `facts_check` and quality gate.

### 7.4 Copy rules (from Samyar's own measured rules)

- No em dashes or en dashes. Commas, colons or full stops.
- Short: about 110 to 125 words of body.
- Personalize with something specific and true from the brief, or leave it out.
- Write as a person: contractions, plain verbs, no marketing register, no fake scarcity
  or drama.
- Credentials and proof stated flatly, never with adjectives; only claims that are true.
- Plain layout: like an email typed in Gmail. No newsletter styling.
- "Hi {first}," or "Hi there," when no name is known.
- One follow-up, in the same thread, then stop. Never send on top of an unanswered reply.
- Prefer a named person over a shared inbox; for a shared inbox, ask who to talk to.

### 7.5 Ship gate

The model ships only if, on held-out test sets it never trained on:
- **Plans:** 100% valid, and more exact matches than the rule parser on the same 300
  requests (a mix of hand-written and paraphrased).
- **Replies:** at least 95% accuracy on a held-out labeled set.
- **Emails:** zero em/en dashes, zero `facts_check` failures, and an average quality
  score at least the built-in writer's (97 on the demo workspace).
- **Answers:** every number matches the result.

If emails miss the bar, 5.4 ships the other three jobs and email writing stays on the
built-in writer until it passes.

**Test sets (Claude's call):**
- The held-out sets are written **before training starts and independently of the rule
  parser**. Expected plans are written by hand from the command and node catalog, never
  copied from parser output, so the comparison isn't circular. A separate reviewer pass
  checks every item. Samyar spot-checks a sample of about 30 in one sitting.
- The test requests are worded differently from the training templates and include
  requests the rule parser is known to get wrong.
- **Exact match means structurally equal plans:** same node types, same edges, same
  settings after filling in defaults. Node IDs, order and display labels are ignored.
  For finds, the same `Query` fields after defaults.
- The scorer and test sets live in `model/eval/` and also run against the rule parser,
  giving the baseline to beat.

## 8. 5.5: The app (T3 Code fork)

### 8.1 What

Fork the web app from `pingdotgg/t3code` (MIT, React + Vite + TypeScript), strip it to
OpenLeads' needs, and match T3 Code's design as closely as possible in OpenLeads'
colors. Samyar's words: "legit fork t3code and match our colourscheme and try to match
their design as much as possible but for our format."

- Keep: the shell, layout, typography, spacing, components, command palette,
  keyboard-first interaction, conversation-in-the-center with a side panel.
- Remove: Clerk auth, Electron/desktop and mobile, their server and provider
  contracts, anything about coding agents.
- **Colors:** OpenLeads' current tokens in `openleads/web/static/styles.css` (light and
  dark), including accent `#2f5ad3` and the good/warn/bad/info scales.
- **Data:** the existing JSON API and NDJSON streams under `/api/*`. New endpoints only
  where the new screens need them.
- **Repo layout (Claude's call):** the app lives in `app/` in this repo; CI builds it
  and the wheel ships the built files. `openleads web` serves them. The Python server
  stays stdlib-only.
- Keep T3 Code's MIT license and copyright notice with the forked code, and list it in
  third-party notices.

### 8.2 Six sections

| Section | Contains |
|---|---|
| **Today** (home) | The briefing (6.3) and the ask box (6.1): type a request, see the plan, run it, watch it stream |
| **People** | people, companies, lists, import, enrich, duplicates, data health |
| **Outreach** | sequences, templates, compose, approve queue |
| **Workflows** | the node editor, runs, templates; old recipes and watchers appear here as graphs |
| **Pipeline** | deals, tasks, analytics, activity |
| **Settings** | settings, mailbox, AI model, ICP scoring, doctor |

The workflow node editor is the largest existing view (about 1,000 lines). Porting it
to React is part of 5.5; how much of `flowgraph.js` is reused is **(builder's call)**.

**Transition (Claude's call):** the old dashboard stays available for one release as

## 11. Growth and scaling

**Targets:** steady daily growth now; 1,000 stars is the goal before monetizing.
Realistically that takes one or two posts reaching a front page (about 30 stars a day
versus 1.5 now), so the 5.5 launch is the main bet and daily posting builds toward it.

posted to X, Bluesky, dev.to (weekly, longer) and GitHub (releases, Discussions).
Tokens are stored as secrets; posts follow each platform's API limits. A short GIF or
screenshot whenever something visual ships.

**Samyar's 15 minutes:** a daily paste queue for Reddit (one community per day,
following its rules), Hacker News and LinkedIn, plus replying to comments in his own
words. Never automated, never through his logged-in browser.

**Also:**
- Fix npm (section 5) so `npx openleads` works again.
- Keep the awesome-list PRs moving; OpenAlternative now qualifies on stars (50+) but
  wants a custom domain.
- Never: mass issues or PRs on other repos, fake engagement, automated replies.

**Scaling the product:** OpenLeads runs locally, so scale means installs and public
data sources, not servers. Watch the public APIs (Overpass, Nominatim) for rate limits
as usage grows; keep caching and polite request pacing. Current live numbers to beat:
median search 51s, 55% of emails backed by public evidence (nightly benchmark,
2026-11-10).
